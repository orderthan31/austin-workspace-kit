# Requirement Intake Normalizer

## 목적

사용자의 피드백이 길고 거칠거나 요구사항이 섞여 있을 때, 바로 구현하지 않고 먼저 이해한 내용을 정리해 보고한다.

이 스킬은 특정 프로젝트, 특정 문서명, 특정 화면명에 묶이지 않는다.

## 트리거

- “내 말 먼저 정리해”
- “문서 고치기 전에 요구사항부터 보고”
- “두서없이 썼으니까 정리해”
- “이해한 거 말해봐”
- 사용자가 화난 상태로 여러 화면/데이터 요구를 한 번에 전달한 경우

## 응답 구조

```md
정리하면 이렇게 이해했습니다.

1. 핵심 변경
2. 화면 구조 영향
3. 데이터/API/상태 영향
4. 기존 기획과 충돌하는 부분
5. 아직 보류하거나 확인할 부분
6. 문서/코드에 반영할 방식
```

## 규칙

- 욕설은 반복하지 않는다.
- 감정은 무시하지 말고 “반복적으로 오해된 지점”을 요구사항으로 고정한다.
- 사용자가 “보고부터”라고 했으면 파일을 수정하지 않는다.
- 사용자가 “맞아”, “가자”, “반영해”라고 승인하면 그때 문서나 코드를 수정한다.
- 사용자가 특정 문서, 코드, 테스트, 브라우저 검증을 제외하라고 하면 제외한다.

## 좋은 정리 예시

```md
정리하면 핵심은 “하위 패널만 바뀌는 구조가 아니라, 상위 탭이 화면의 주요 영역 전체를 교체해야 한다”입니다.

반영 기준:
- 상위 탭은 전체 화면 구조를 교체한다.
- 하위 탭은 선택된 상위 흐름 안에서만 동작한다.
- 서로 다른 업무 흐름은 같은 영역을 재사용하지 않고 독립 화면으로 분리한다.
```

## 금지

- “아마 이런 뜻일 것 같습니다”만 말하고 끝내지 않는다.
- 승인 없이 문서, 코드, 칸반, 외부 노트를 고치지 않는다.
- 모호한 요구를 구현 태스크로 바로 확정하지 않는다.
