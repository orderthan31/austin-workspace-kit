## 1. 목표

프로젝트 전체 문맥을 깊이 분석하고 파악한 뒤, 사용자의 요청을 구현 친화적인 작업 명세로 다시 정리하고,
이를 검증 가능한 작업 단위로 분해하여 프로젝트 루트에 `plan.md`를 생성 또는 업데이트한다.

- 출력 파일: `plan.md` (프로젝트 루트)
- 출력 성격: 실행 순서, 범위, 의존성, 리스크, 검증 기준, 구현 진입점이 있는 구체 계획
- 핵심 목적: 구현 스킬이 불필요하게 전체 프로젝트를 다시 뒤지지 않도록 task별 좁은 컨텍스트를 제공한다.
- 후속 단계: 계획 작성 전에 이 작업이 기존 플랜 확장인지, 기존 플랜 백업 후 새 플랜 시작인지 먼저 판단한다. 그 뒤에 맞는 `obsidian-plan-register` / `obsidian-plan-reset` 흐름으로 넘긴다.

## 2. 적용 시점

- 사용자가 기능/리팩터링/마이그레이션의 상세 계획을 요청할 때
- 요구사항은 있으나 구현 순서와 범위가 불명확할 때
- 큰 작업을 착수 전에 단계별로 확정해야 할 때

## 3. 입력

- 사용자 제안 항목(필수)
- 프로젝트 루트 경로(명시 없으면 현재 작업 디렉터리)
- 제약 조건(마감, 호환성, 인력, 기술 스택 등)

## 3.5 질문 정제 규칙

사용자 질문이 거칠거나 두루뭉술해도 그대로 옮겨 적지 않는다. 먼저 아래 순서로 작업용 문장으로 정제한다.

1. 사용자 원문에서 진짜 목표를 추출한다.
2. 불만/증상/희망사항을 개발 작업 언어로 다시 쓴다.
3. 이번 사이클에서 할 것과 하지 않을 것을 분리한다.
4. 구현자가 바로 움직일 수 있도록 파일, 검색 키워드, 완료 기준까지 붙인다.

예시:

- 원문: "여기 렉 걸리는데 고쳐"
- 정제: "`editor/work` 페이지에서 입력 변경 시 과도한 리렌더가 발생하므로 상태 업데이트 경로와 구독 범위를 축소하는 작업을 계획한다."

## 4. 표준 절차

1. 사용자 요청을 작업 언어로 다시 정리한다.
   - 원문, 정제된 목표, 제외 범위를 분리한다.
2. 프로젝트 구조를 스캔한다.
   - 핵심 디렉터리, 엔트리 포인트, 빌드/테스트 명령, 설정 파일을 확인한다.
3. 현재 동작 기준선을 확인한다.
   - 가능한 경우 테스트/린트/빌드 명령 존재 여부를 파악한다.
4. 사용자 제안 항목을 작업 단위로 분해한다.
   - 기능 단위, 데이터 단위, 배포 단위로 나누되 구현자가 한 번에 처리 가능한 크기로 자른다.
5. 각 항목에 대해 영향을 받는 코드 영역을 매핑한다.
   - 파일/모듈/인터페이스/데이터 계약 단위로 연결한다.
6. 각 작업에 대한 `Task Context Pack`을 만든다.
   - 수정 예상 파일, 참고 파일, 제외 파일, 검색 키워드, 완료 기준, 검증 방법을 적는다.
7. 의존성과 선후관계를 확정한다.
   - 선행 작업 없이는 진행 불가한 항목을 명시한다.
8. 리스크와 대응 전략을 정의한다.
   - 기술 리스크, 운영 리스크, 일정 리스크를 분리한다.
9. 검증 기준을 정의한다.
   - 완료 조건(DoD), 테스트 기준, 롤백 기준을 항목별로 적는다.
10. 이 요청이 기존 플랜을 이어받는지, 새 플랜으로 갈아타는지 판단한다.
   - 아래 `플랜 처리 결정 규칙`을 따른다.
11. `plan.md`를 작성한다.
   - 아래 템플릿을 기준으로 구체적인 일정/작업/검증 항목을 채운다.
   - 구현 스킬이 이 문서만 보고 현재 task에 진입할 수 있어야 한다.
12. 구현 전 handoff를 준비한다.
   - `현재 플랜 확장`이면 기존 `agents-plan` 등록본 앵커를 유지한 채 그 plan을 계속 사용한다.
   - `기존 플랜 백업 후 새 플랜 시작`이면 먼저 `obsidian-plan-reset` 또는 기존 등록본 정리를 통해 이전 사이클을 닫고, 새 `plan.md`에 대해 `obsidian-plan-register`를 실행한다.

## 4.5 플랜 처리 결정 규칙

deep-planning은 새 계획을 쓰기 전에 아래 둘 중 하나를 먼저 결정한다.

1. `현재 플랜 확장`
2. `기존 플랜 백업 후 새 플랜 시작`

### 4.5.1 `현재 플랜 확장`으로 보는 경우

- 현재 `plan.md`의 목표와 이번 요청의 목표가 같은 축이다.
- 기존 task/phase를 이어서 더 세분화하거나 후속 작업만 추가하면 된다.
- 기존 플랜의 산출물, acceptance 기준, active plan 링크를 그대로 쓰는 편이 자연스럽다.
- 예:
  - 테스트 플랜에 보안 수정 task를 추가
  - 같은 parser 개선 플랜에 후속 fixture/task만 추가
  - 진행률 30%인 리팩토링 플랜에 Phase 2~3을 덧붙임

### 4.5.2 `기존 플랜 백업 후 새 플랜 시작`으로 보는 경우

- 현재 플랜의 주된 목표가 사실상 끝났다.
- 이번 요청이 다른 축의 작업이라 기존 플랜에 붙이면 제목/범위가 어색해진다.
- 같은 파일에 계속 덧붙이면 "중간 플랜"이 쌓여 가독성이 나빠진다.
- 예:
  - surgeries 동기화 플랜 완료 후 병원코드 매핑 플랜 시작
  - parser 개선 플랜 종료 후 성능 최적화 플랜 시작
  - 현재 플랜 범위 밖의 대형 리팩토링으로 전환

### 4.5.3 애매할 때 기본 원칙

- "같은 목표를 더 밀어붙이는 것"이면 `현재 플랜 확장`
- "새 목표로 사이클을 바꾸는 것"이면 `기존 플랜 백업 후 새 플랜 시작`
- 둘 다 조금씩 섞였더라도, 새 작업의 제목을 기존 요약명으로 설명하기 어색하면 새 플랜으로 분리한다.

## 6. 작성 규칙

- 추상적 문장 대신 파일/모듈/인터페이스 기준으로 작성한다.
- 사용자 원문을 그대로 반복하지 말고 구현 가능한 작업 문장으로 다시 써서 `Problem Restatement`에 남긴다.
- `## 한 줄 요약`은 꼭 채운다. 이 값은 `agents-plan/MM-DD/<한 줄 요약>.md` 경로의 기본 재료다.
- `한 줄 요약`에는 사용자 원문, 긴 설명문, 조사형 문장 전체를 넣지 않는다.
- `한 줄 요약`은 "무엇을 하는 플랜인지"만 짧게 드러나게 쓴다.
- 플랜 안에 날짜/시간/로그를 적을 때는 항상 KST 기준으로 적는다.
- 상대 시간 표현보다 절대 시간 표현을 우선한다. 예: `2026-03-24 14:30 KST`
- 길이는 가능하면 10~30자 안팎으로 유지한다.
- `## 플랜 처리 결정`은 꼭 채운다.
- `현재 플랜 확장`으로 결정했으면 기존 `agents-plan` 등록본을 계속 active로 유지한다.
- `기존 플랜 백업 후 새 플랜 시작`으로 결정했으면 이전 사이클을 닫고 새 `obsidian-plan-register`를 실행하는 흐름을 따른다.
- 각 단계는 "무엇을 변경하는지 + 어떻게 검증하는지"를 함께 적는다.
- 사용자 제안 항목은 누락 없이 반영하되, 범위 밖 항목은 `Out of scope`로 분리한다.
- 불확실성이 크면 `Assumptions`와 확인 필요 항목을 명시한다.
- 각 task에는 반드시 아래 항목이 있어야 한다.
  - `수정 예상 파일`
  - `참고 파일`
  - `제외 파일`
  - `검색 키워드`
  - `완료 기준`
  - `검증 방법`
- `수정 예상 파일`은 구현자가 첫 진입 시 우선 열어볼 파일 3~7개 정도로 압축한다.
- `제외 파일`은 이번 작업에서 보지 않아도 되는 영역을 명시해 구현 스킬의 탐색 범위를 줄인다.
- `Task Context Pack`만 읽어도 현재 task 구현을 시작할 수 있어야 한다.
- 구현 단계로 넘기기 전 `obsidian-plan-register`를 먼저 실행해 `agents-plan` 등록본 링크를 확보하는 것을 기본 절차로 본다.
- daily / project 카드 / review에서 참조할 플랜 링크는 가능하면 루트 `plan.md`보다 `agents-plan` 등록본을 우선한다.
