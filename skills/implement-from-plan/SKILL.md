## 1. 목표

`plan.md`를 실행 문서로 사용하되, plan 전체를 다시 설계하지 말고 현재 task의 `Task Context Pack`을 기준으로 실제 코드를 구현한다.

- 입력: 프로젝트 루트 `plan.md`
- 출력: 코드 변경 + 테스트/검증 결과 + 갱신된 `plan.md`
- 부가 출력: 태스크별 Obsidian 작업 로그(`obsidian-daily-ops` 스킬로 기록)
- 핵심 목적: 구현 단계에서 불필요한 전체 코드베이스 재탐색을 줄인다.
- 선행 조건: 구현 전에 `obsidian-plan-register` 등록본 링크를 확보하는 것을 기본값으로 본다.

## 2. 적용 시점

- `plan.md`가 이미 작성되어 있고 구현 단계로 넘어갈 때
- 단계별 체크박스를 기준으로 순차 구현이 필요할 때
- 우선순위/의존성을 지키며 안정적으로 배포까지 진행할 때

## 3. 표준 절차

1. `plan.md`를 읽고 미완료 항목(`- [ ]`, `⬜`)을 수집한다.
2. `## 플랜 처리 결정` 섹션을 먼저 읽는다.
   - `현재 플랜 확장`이면 기존 active plan 앵커를 그대로 사용한다.
   - `기존 플랜 백업 후 새 플랜 시작`이면 이전 플랜이 닫혔는지 확인하고, 현재 `plan.md`는 새 `obsidian-plan-register` 등록본을 갖고 있어야 한다.
3. `obsidian-plan-register`로 이 plan의 `agents-plan` 등록본이 있는지 먼저 확인한다.
   - 없다면 구현 전에 먼저 등록해 daily와 project 카드가 참조할 plan 앵커를 만든다.
   - 등록 앵커 없이 바로 구현하는 것은 예외 상황으로 본다.
4. 선행 작업(`Depends on`, 단계 의존성)을 확인해 실행 순서를 확정한다.
5. 이번 사이클 범위를 고정한다.
   - 기본: 한 번에 1개 작업만 선택
   - 고위험 변경은 더 작은 단위로 분할
6. 선택된 작업의 `Task Context Pack`을 읽는다.
   - `목적`, `수정 예상 파일`, `참고 파일`, `제외 파일`, `검색 키워드`, `완료 기준`, `검증 방법`을 먼저 확인한다.
7. 구현 전 기준선을 확인한다.
   - 관련 테스트/린트/빌드 명령과 영향 파일을 점검하되 `수정 예상 파일`부터 본다.
8. 선택된 작업을 구현한다.
   - 작업별로 코드 변경 후 즉시 최소 검증을 수행한다.
   - 정보가 부족할 때만 `참고 파일`과 인접 파일로 탐색을 넓힌다.
9. 각 작업이 끝날 때마다 `obsidian-daily-ops`를 호출해 당일 `Details (Agent Log)`에 기록한다.
   - 최소 기록 항목: 작업 ID, 목적, 수행내용, 결과, 이슈(없으면 없음), 핵심 파일 경로
   - 관련 플랜은 가능하면 루트 `plan.md`가 아니라 `agents-plan` 등록본 위키링크를 같이 남긴다.
   - 코드 수정이 없더라도 원인 분석, 테스트 실패, 차단 확인 같은 의미 있는 진전은 기록한다.
10. 검증을 통과한 항목만 완료 처리한다.
   - 실패 항목은 체크하지 않고 원인/후속 조치를 기록한다.
11. `plan.md`를 갱신한다.
   - 완료 체크, 진행률, 완료/잔여 개수, 이슈를 반영한다.
12. 이번 구현으로 프로젝트의 현재 상태/결정/리스크가 바뀌었다면 `obsidian-context-ingest` 승격 필요 여부를 판단한다.

## 4. 구현 규칙

- `plan.md`에 없는 작업은 원칙적으로 수행하지 않는다.
- 구현 시작 전 `obsidian-plan-register` 등록본을 확보하고, 그 링크를 기록용 플랜 앵커로 사용한다.
- `## 플랜 처리 결정`이 `현재 플랜 확장`이면 새 플랜을 따로 만들지 않는다.
- `## 플랜 처리 결정`이 `기존 플랜 백업 후 새 플랜 시작`인데도 이전 플랜 정리가 안 되어 있으면, 구현 전에 먼저 planning/plan 정리 단계로 되돌린다.
- 현재 task의 `Task Context Pack`을 우선하며, plan 전체를 다시 설계하려고 하지 않는다.
- `수정 예상 파일`을 먼저 읽고, 필요할 때만 `참고 파일`과 근처 파일로 넓힌다.
- `제외 파일`과 `제외 범위`는 특별한 근거가 없으면 읽거나 수정하지 않는다.
- 불가피한 추가 작업이 필요해도 구현 단계에서 plan 구조를 임의로 바꾸지 않는다.
- 추가 작업이 필요하면 차단 사유와 함께 planning 재진입이 필요하다고 기록한다.
- 각 작업은 아래 4가지를 모두 만족해야 완료 처리한다.
  - 코드 반영
  - 검증(테스트/린트/수동 검증) 통과
  - `obsidian-daily-ops` 호출로 작업 로그 기록
  - 영향 범위 설명 가능
- 작업이 프로젝트 상태를 실질적으로 바꿨다면, `obsidian-context-ingest` 승격 판단까지 해야 "완전 종료"로 본다.
- 대규모 변경은 단계별 커밋 가능한 단위로 쪼개서 진행한다.
- `plan.md`의 `구현 로그` 시간은 항상 KST로 적는다.
- 실행 환경 시간이 UTC/미국 시간이어도, 로그에 적기 전 KST로 바꾼다.

## 4.2 구현 전/후 고정 루프

구현 스킬은 아래 루프를 기본으로 따른다.

### 구현 전

1. active plan 앵커가 있는지 확인한다.
2. 없으면 `obsidian-plan-register`를 먼저 수행한다.

### 각 작업 후

1. 검증 결과를 정리한다.
2. `obsidian-daily-ops`로 같은 사실을 남긴다.

### 사이클 종료 전

1. `plan.md` 상태를 최신화한다.
2. project 카드 승격이 필요한지 판단한다.

쉽게 말하면:

- 구현 전에 plan 앵커를 만든다.
- 작업 후에는 daily에 남긴다.
- 큰 상태 변화가 있으면 project에도 반영한다.

## 4.5 컨텍스트 사용 규칙

- 기본 원칙은 "현재 task 하나, 관련 파일 몇 개"다.
- 기본 원칙은 "현재 task 하나, 관련 파일 몇 개, 링크 가능한 plan 앵커 하나"다.
- `Task Context Pack`에 적힌 `수정 예상 파일`만으로 진입 가능한지 먼저 판단한다.
- `검색 키워드`를 활용해 필요한 정의 위치를 빠르게 찾되, 무관한 디렉터리 전체 스캔은 지양한다.
- task 수행 중 범위 밖 수정이 필요하면 즉시 멈추고 아래를 기록한다.
  - 왜 현재 task 범위를 넘는지
  - 어떤 추가 계획이 필요한지
  - 지금 진행 가능한 우회가 있는지
- 구현 스킬은 새로운 계획 작성자가 아니라, 주어진 task를 좁게 수행하는 실행자라는 점을 유지한다.

## 5. plan.md 갱신 규칙

### 5.1 체크 상태

- 단계 작업: `- [ ]` -> `- [x]`
- 작업 분해 표: `⬜` -> `✅` (미완료는 `⬜` 유지)
- 마일스톤: 조건 충족 시 `- [x]`로 변경

### 5.2 진행률 계산

- 전체 진행률 = `(완료 작업 수 / 전체 작업 수) * 100`
- 소수점은 반올림해 정수 `%`로 기록
- `진행 현황 요약`의 3개 값을 항상 함께 갱신
  - 전체 진행률
  - 완료된 항목 수
  - 남은 항목 수

### 5.3 상태 기록

`plan.md` 하단에 아래 섹션을 유지/추가한다.

```markdown
## 10) 구현 로그
- YYYY-MM-DD HH:mm KST: 작업 ID/이름, 변경 파일, 검증 결과, 메모
```

## 6. 실패/차단 대응

- 테스트 실패 시 체크를 되돌리고 원인을 `구현 로그`에 남긴다.
- 테스트 실패/차단 상황도 `obsidian-daily-ops`로 동일하게 기록한다.
- `Task Context Pack` 정보가 부족해 구현 진입 자체가 불명확하면 이를 실패가 아니라 계획 부족으로 기록한다.
- `agents-plan` 등록본이 없어서 daily에 관련 플랜 링크를 안정적으로 남길 수 없으면 구현 전에 `obsidian-plan-register` 선행이 필요하다고 기록한다.
- 외부 의존성/스펙 불명확으로 막히면 다음을 기록한다.
  - 차단 원인
  - 필요한 결정 사항
  - 임시 우회 가능 여부
- 차단된 작업은 후순위 독립 작업으로 전환 가능한지 즉시 판단한다.
