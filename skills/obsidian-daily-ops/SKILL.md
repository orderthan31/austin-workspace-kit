## 0. 공통 실행 원칙

- 이 스킬은 `obsidian-cli-guideline` 기준을 따른다.
- daily 노트 수정은 markdown 파일 직접 편집으로 처리한다.
- 기록과 요약을 따로 나누지 말고 같은 날 노트 안에서 연결되게 관리한다.
- 날짜와 시간은 항상 KST 기준으로 해석하고 기록한다.
- issue 칸반 완료 기록과 함께 남기는 경우, daily 기록 날짜와 issue 카드의 완료 메타(`✅ YYYY-MM-DD`)가 가능하면 같게 유지한다.
- `오늘 날짜`는 KST의 오늘을 뜻한다. 다른 시간대 기준 날짜를 그대로 쓰지 않는다.
- 같은 프로젝트에서 하루에 플랜이 여러 개 생겨도 daily는 플랜 저장소가 아니라 "대표 활성 플랜 요약판"으로 유지한다.
- 읽는 순서는 `요약 -> 근거`가 더 자연스럽다고 보고, `오늘 한일 Summary`를 `Details (Agent Log)`보다 위에 둔다.
- `오늘 한일 Summary`와 체크박스 todo는 사람에게 보고하는 층이다. 여기에는 `T1`, `Phase 3`, `P1-2` 같은 내부 작업 ID를 기본적으로 쓰지 않는다.
- 내부 작업 ID는 `Details (Agent Log)`의 `linked_todo` 또는 플랜 문서 안에 남긴다.

## 1. 목표

하루 작업의 `근거`, `요약`, `플랜 연결`을 daily 노트 한 곳에 모은다.

- 대상 파일: `$OBSIDIAN_ROOT/daily/YYYY-MM-DD.md`
- 핵심 결과:
  - `오늘 한일 Summary` 갱신
  - `Details (Agent Log)` 갱신
  - `오늘 할일` 자동 보강
  - 관련 플랜/프로젝트 노트 링크 유지
  - 같은 날 여러 플랜이 생겨도 대표 활성 플랜 1개만 우선 노출

이 스킬은 특정 플랜 구현 때만 쓰는 보조 도구가 아니다.
에이전트가 수행한 모든 의미 있는 작업을 옵시디언에 남길 때 가장 먼저 거치는 기본 기록 허브다.

쉽게 말하면:

- 코드 수정도 기록
- 분석만 했어도 기록
- 실패했어도 기록
- 이슈 상태만 바꿨어도 기록

이게 기본이다.

## 2. 제텔카스텐 연결 원칙

daily 노트는 "하루 로그"이면서 동시에 다른 노트로 가는 허브다.

반드시 연결할 것:

1. 관련 플랜 스냅샷 노트
2. 관련 프로젝트 노트 또는 대표 개념 노트
3. linked_todo에 대응하는 작업 근거

주의:

- daily에는 플랜 링크를 줄줄이 나열하지 않는다.
- 같은 프로젝트에서 같은 날 여러 플랜이 생겨도 `연결 노트`에는 프로젝트 헤더 아래에 "오늘 실제로 작업한 독립 플랜"만 불릿 리스트로 정리한다.
- 화살표 체인(`A -> B -> C`) 한 줄 나열은 쓰지 않는다.
- `현재 활성 플랜` 1개는 꼭 남기고, 같은 날 실제로 손댄 다른 플랜 중에서도 별도 흐름인 것만 같은 프로젝트 아래 불릿으로 정리한다.
- 현재 활성 플랜으로 흡수된 중간 플랜, 같은 목표의 확장 플랜, 이름만 잠깐 바뀐 플랜은 따로 적지 않는다.
- 자세한 플랜 이력은 프로젝트 카드의 `플랜 관리` 섹션에서 다룬다.

권장 링크 형식:

- 활성 plan: `[[agents-plan/MM-DD/<한 줄 요약>]]`
- archive plan: `[[archive/agents-plan/YYYY/MM/<한 줄 요약>]]`
- `[[daily/YYYY-MM-DD]]`
- `[[weekly/YYYY-[W]WW]]`
- `[[monthly/YYYY-MM]]`
- `[[projects/projects]]`
- `[[프로젝트 A]]`, `[[프로젝트 B]]` 같은 프로젝트 핵심 노트
- 필요하면 `[[프로젝트 A]] [[롯데구축]]`처럼 상위/하위 프로젝트를 같이 적기

쉽게 말하면:

- daily는 "오늘 무슨 일이 있었는지"
- plan은 "왜 그 일을 했는지"
- project note는 "이 일이 전체 맥락에서 뭔지"

이 셋이 연결돼야 한다.

## 3. 입력 계약

- 필수:
  - `date` 또는 오늘 날짜(KST 기준)
  - `project_name`
- 선택:
  - `task_type` (`analysis` | `planning` | `implementation` | `verification` | `issue-triage` | `bugfix` | `documentation` | `ops`)
  - `parent_project`
  - `work_title`
  - `purpose`
  - `action`
  - `result`
  - `issue`
  - `outcome_status` (`done` | `in_progress` | `blocked` | `failed`)
  - `linked_todo`
  - `plan_note`
  - `issue_note`
- `project_note`
  - `active_plan_note`
  - `plan_change_summary`
  - `plan_change_count`
  - `state_changed=true|false`
  - `promote_project_update=true|false`
  - `summarize=true|false`

입력이 로그 기록용이면 `work_title/action/result`가 필요하다.
입력이 마감 요약용이면 `summarize=true` 또는 equivalent intent면 된다.

기본 해석:

- 값이 일부 비어 있어도 "이번 작업을 daily에 남겨야 한다"는 판단이 서면 가능한 정보만으로 먼저 기록한다.
- 특히 분석, 조사, 실패, 차단은 코드 변경이 없어도 기록 대상이다.

## 3.1 todo 자동 보강 규칙

로그를 추가할 때 아래 순서로 `오늘 할일`도 같이 본다.

1. `linked_todo`가 이미 `오늘 할일` 또는 `이월된 할일`에 있으면 그 줄을 재사용한다.
2. 없으면 `work_title`을 10~20자 안팎의 짧은 todo 문장으로 줄여 `오늘 할일`에 새 줄을 만든다.
3. 이미 끝난 일이라면 `[x]`, 아직 진행 중이면 `[ ]`로 적는다.
4. 같은 뜻의 줄이 이미 있으면 새로 만들지 말고 기존 줄을 더 깔끔하게 다듬는다.

좋은 예:

- `다회사 처리 코드 품질 분석 및 리팩토링 착수` -> `다회사 리팩토링 착수`
- `보안 취약점 스캔 및 수정` -> `보안 취약점 수정`
- `total_medication_days plan T2~T8 closeout` -> `total_medication_days 플랜 정리`
- `pytest 회귀 실패 5건 안정화` -> `pytest 회귀 5건 안정화`

## 4. 출력 계약

- 수정 파일:
  - `$OBSIDIAN_ROOT/daily/YYYY-MM-DD.md`
- 수정 결과:
  - `## 연결 노트` 섹션 유지 또는 보강
  - `## 오늘 할일` 자동 보강
  - `오늘 한일 Summary` 갱신
  - `Details (Agent Log)` 항목 추가/정리

## 5. 대상 구조

daily 노트는 가능하면 아래 흐름을 유지한다.

1. 연결 노트
2. 이월된 할일 / 오늘 할일
3. 오늘 한일 Summary
4. Details (Agent Log)

프로젝트별 플랜 표기 원칙:

1. `연결 노트`는 프로젝트별 `###` 헤더 구조를 우선한다.
2. 각 프로젝트마다 `현재 활성 플랜` 1개는 꼭 둔다.
3. 같은 날 실제로 작업한 다른 플랜이 있으면 같은 프로젝트 아래에 불릿으로 추가한다.
4. 다만 현재 활성 플랜에 흡수된 중간 플랜은 추가하지 않는다.
5. 상세 변경 내역은 project 카드의 `플랜 관리`로 보낸다.

## 5.1 이 스킬이 기본 허브인 이유

다른 스킬은 각자 자기 일을 한다.
하지만 "오늘 무슨 일이 있었는가"를 모으는 기준점은 daily 하나로 고정해야 한다.

그래서 다른 스킬이 아래 일을 했다면, 끝난 뒤에는 이 스킬로 이어지는 것을 기본으로 본다.

- `deep-planning`
- `implement-from-plan`
- `issue-tracker`
- `obsidian-plan-register`
- `obsidian-plan-reset`
- 기타 분석/조사/운영 작업

즉, 어떤 작업을 했든 마지막에 daily로 모이게 만드는 허브가 이 스킬이다.

## 6. 표준 절차

### 6.0 공통 진입 규칙

1. "이번 작업이 의미 있는 작업인가?"를 먼저 판단한다.
2. 아래 중 하나라도 해당하면 기록 대상으로 본다.
   - 코드를 수정했다
   - 원인을 분석했다
   - 플랜을 만들거나 바꿨다
   - 테스트/검증을 수행했다
   - 이슈 상태를 옮겼다
   - 실패/차단을 확인했다
3. 기록 대상이면 이 스킬을 호출한다.
4. 작업이 project 카드까지 바꿔야 할 수준이면 `promote_project_update=true` 후보로 본다.

### 6.1 로그 기록

1. 대상 daily 파일을 찾는다. 없으면 템플릿으로 생성한다.
2. `## 연결 노트`에 관련 플랜/프로젝트 허브/프로젝트 노트 링크가 있는지 확인한다.
3. `오늘 할일`에 해당 작업이 이미 있는지 먼저 본다.
4. 없으면 `linked_todo` 또는 `work_title`을 짧게 줄여 새 todo 1줄을 추가한다.
5. 해당 프로젝트의 `### Project:` 섹션을 찾는다.
6. `Details (Agent Log)`에 작업 항목을 추가한다.
7. `active_plan_note`가 있으면 그 링크를 우선 사용한다.
8. `plan_note`만 있고 `active_plan_note`가 없으면 `plan_note`를 사용한다.
9. 같은 날 플랜이 여러 번 바뀌었으면 `연결 노트`에서는 프로젝트 헤더별 불릿 리스트로 정리한다.
10. `현재 활성 플랜` 1개 + 그날 실제 작업한 별도 관련 플랜 불릿 몇 개만 남긴다.
11. 현재 활성 플랜에 흡수된 중간 플랜은 `연결 노트`에 남기지 않는다.
12. `issue_note` 또는 관련 이슈가 있으면 로그 본문에 같이 남긴다.
13. `outcome_status`가 `blocked` 또는 `failed`면 Summary에도 과장 없이 드러나게 반영한다.

### 6.2 마감 요약

1. 같은 daily의 `Details (Agent Log)`를 읽는다.
2. 프로젝트별로 `완료/진행 중/블로커`를 정리한다.
3. `오늘 한일 Summary`를 갱신한다.
4. 요약 문장에는 현재 활성 플랜 1개만 같이 둔다.
5. 필요하면 `오늘 플랜 변경 횟수: N` 정도만 적고 상세 파일 목록은 생략한다.
6. `완료/진행 중/블로커` 문장은 task 번호 대신 결과와 상태를 먼저 쓴다.

### 6.3 프로젝트 이름 규칙

1. 저장소명이나 워크트리명보다 프로젝트 문서 제목을 우선한다.
2. 예: `claim-q-front` 대신 `[[프로젝트 A]]`
3. 세부 트랙이 있으면 상위/하위 프로젝트를 함께 적는다.
4. 예: `[[프로젝트 A]] [[롯데구축]]`
5. 코드 경로나 실제 파일명 안의 저장소명은 바꾸지 않는다.

### 6.4 같은 날 플랜이 여러 개인 경우

1. daily `연결 노트`에서는 프로젝트별 `###` 헤더로 묶는다.
2. 현재 활성 플랜 1개는 첫 줄에 둔다.
3. 그날 실제로 손댄 다른 플랜은 같은 프로젝트 아래 불릿 리스트로 둔다.
4. 현재 활성 플랜의 연장선으로 흡수된 중간 플랜은 적지 않는다.
5. 화살표 체인 한 줄은 쓰지 않는다.

예:

### [[프로젝트 A]]
- 현재 활성 플랜: `[[agents-plan/03-19/테스트-커버리지-보안-수정]]`
- 오늘 작업한 플랜:
  - `[[agents-plan/03-19/다회사-처리-코드-품질-리팩토링]]`

6. 자세한 파일별 이력은 프로젝트 카드의 `플랜 관리`에서 본다.

### 6.5 오늘 할일 자동 정리

1. `오늘 할일`에 없는 일을 실제로 했으면 짧은 한 줄 todo를 추가한다.
2. 이미 끝난 일이면 `[x]`로 추가하고, 진행 중이면 `[ ]`로 추가한다.
3. `이월된 할일`에서 끝난 것은 `[x]`로 갱신한다.
4. `오늘 할일`과 `이월된 할일`에 같은 뜻의 문장이 중복되면 더 짧고 읽기 쉬운 문장 하나로 정리한다.
5. todo 문장은 로그 문장보다 짧아야 한다.
6. todo 문장은 가능하면 아래 순서로 만든다.
   - 프로젝트명
   - 핵심 동사 1개
   - 대상 1개

예:

- 길다: `현재 플랫폼 브랜치에서 여러개의 회사를 동시 처리하면서 코드가 지저분해진 부분 점검`
- 좋다: `[[프로젝트 A]] 다회사 코드 점검`

## 7. 기록 형식

```markdown
## 연결 노트
### [[<project-name>]]
- 현재 활성 플랜: [[agents-plan/MM-DD/<한 줄 요약>]]
- 오늘 작업한 플랜:
  - [[agents-plan/MM-DD/<다른 플랜 요약>]]

### [[<project-note>]]
- 현재 활성 플랜:
- 오늘 작업한 플랜:

- 프로젝트 허브: [[projects/projects]]
- 이번 주: [[weekly/YYYY-[W]WW]]

## 오늘 할일
- [x] [[<project-name>]] <짧은 todo>

## 오늘 한일 Summary

### Project: [[<project-name>]]
- 현재 활성 플랜: [[agents-plan/MM-DD/<한 줄 요약>]]
- 완료:
- 진행 중:
- 블로커:

## Details (Agent Log)

### Project: [[<project-name>]]
- 현재 활성 플랜: [[agents-plan/MM-DD/<한 줄 요약>]]
- 오늘 플랜 변경: <없음 또는 짧은 요약>
- [HH:MM KST] <작업 제목>
  - linked_todo: <체크박스 문구 또는 ID>
  - 목적: <왜 했는지>
  - 수행내용: <무엇을 했는지>
  - 결과: <무엇이 바뀌었는지>
  - 이슈: <문제/리스크/없음>
```

## 8. Summary 형식

```markdown
### Project: [[<project-name>]]
- 현재 활성 플랜: [[agents-plan/MM-DD/<한 줄 요약>]]
- 오늘 플랜 변경 횟수: 0
- 완료: <핵심 완료 1~3개>
- 진행 중: <진행 중 항목>
- 블로커: <의존성/결정 필요사항/없음>
```

## 9. 실패 시 처리

- daily 파일이 없으면 생성 후 진행한다.
- 프로젝트 섹션이 없으면 새로 만든다.
- `Details` 근거가 부족하면 Summary를 과장해서 쓰지 않는다.
- plan 링크를 모르면 비워두지 말고 나중에 채울 수 있게 `관련 플랜 미확정` 한 줄을 남긴다.
- 같은 날 여러 플랜이 있어도 daily에 전부 나열하지 않는다.
- 어느 플랜이 현재 활성인지 모르면 `현재 활성 플랜 미확정`으로 적고 project 카드에서 먼저 정리한다.
- project 카드 승격이 애매하면 먼저 daily에는 남기고, project 반영은 보류한다.
- `오늘 할일`이 비어 있는데 실제 작업 로그가 있으면 최소 1줄 이상 자동 보강한다.
- todo를 자동 생성할 때는 긴 설명문을 그대로 복사하지 말고 한 줄 요약으로 줄인다.
- 외부 도구가 UTC/다른 시간대로 시간을 줬다면 daily에 적기 전에 반드시 KST로 변환한다.
