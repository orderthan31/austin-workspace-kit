## 0. 공통 실행 원칙

- 이 스킬은 `obsidian-cli-guideline` 기준을 따른다.
- 읽고 쓰는 모든 노트 경로는 `OBSIDIAN_ROOT` 기준이다.
- 현재 코드 프로젝트 `cwd`가 다른 곳이어도 `projects/...`, `daily/...`, `agents-plan/...`, `prompt/review/...` 는 vault 상대경로로 해석한다.
- 원문 로그를 길게 복사하지 말고, 프로젝트 카드에 필요한 사실만 압축 반영한다.
- 프로젝트 카드가 이미 있으면 덧붙이기보다 최신 상태로 정리한다.

## 1. 목표

`daily`, `agents-plan`, `prompt/review` 같은 노트에 흩어진 중요한 사실을 프로젝트 카드로 승격한다.

- 대상 파일:
  - `$OBSIDIAN_ROOT/projects/<project>.md`
- 주요 입력 후보:
  - `$OBSIDIAN_ROOT/daily/YYYY-MM-DD.md`
  - `$OBSIDIAN_ROOT/agents-plan/MM-DD/*.md`
  - `$OBSIDIAN_ROOT/archive/agents-plan/YYYY/MM/*.md`
  - `$OBSIDIAN_ROOT/prompt/review/*.md`
- 핵심 결과:
  - 프로젝트 카드의 `현재 상태` 최신화
  - `활성 컨텍스트` 링크 최신화
  - `최근 결정`, `최근 블로커 / 리스크` 갱신
  - 필요 시 `자주 보는 경로 / 아티팩트` 보강

쉽게 말하면:

- raw layer에서 중요한 사실을 뽑고
- retrieval layer인 프로젝트 카드에 올리는 스킬이다.

이 스킬은 "나중에 한번 정리하는 선택 기능"이 아니라, 작업 결과가 프로젝트 상태를 실질적으로 바꿨을 때 호출하는 승격 허브다.

즉 아래 같은 변화가 있으면 이 스킬 호출 후보로 본다.

- 현재 활성 플랜이 바뀜
- 주요 결정이 바뀜
- 살아 있는 리스크가 새로 생김
- 블로커가 해소됨
- 프로젝트의 현재 단계가 바뀜

## 2. 입력 계약

- 필수:
  - `project_name`
- 선택:
  - `source_date`
  - `daily_note`
  - `plan_note`
  - `review_note`
  - `max_decisions` (기본 3)
  - `max_risks` (기본 3)
  - `update_links=true|false` (기본 true)

입력이 비어 있으면 아래 우선순위로 소스를 찾는다.

1. 최근 daily에서 해당 프로젝트 섹션
2. 최근 agents-plan 중 해당 프로젝트 관련 문서
3. 최근 review 중 해당 프로젝트와 운영 패턴 관련 문서

## 3. 출력 계약

- 수정 파일:
  - `$OBSIDIAN_ROOT/projects/<project>.md`
- 수정 섹션:
  - `## 현재 상태`
  - `## 활성 컨텍스트`
  - `## 최근 결정`
  - `## 최근 블로커 / 리스크`
  - `## 자주 보는 경로 / 아티팩트`

## 4. 대상 구조

이 스킬은 프로젝트 카드를 아래 순서로 갱신한다.

1. 현재 상태
2. 활성 컨텍스트
3. 최근 결정
4. 최근 블로커 / 리스크
5. 자주 보는 경로 / 아티팩트

원문을 그대로 붙이지 않고, "지금 읽어야 할 정보"만 남긴다.

## 5. 표준 절차

### 5.1 소스 수집

1. 대상 프로젝트 카드를 연다.
2. 최근 daily에서 해당 프로젝트 섹션을 찾는다.
3. 최근 plan 중 현재 활성 plan 후보를 찾는다.
4. 최근 review 중 운영상 주의할 점이 있으면 찾는다.

다른 스킬과의 연결 기본값:

1. 모든 의미 있는 작업은 먼저 `obsidian-daily-ops`에 남긴다.
2. 그중 project 카드까지 올라가야 할 상태 변화만 이 스킬로 승격한다.

즉 `daily`가 원장이고, 이 스킬은 그중 중요한 사실만 project 카드로 올리는 필터다.

### 5.2 사실 추출

아래 유형만 추린다.

1. 지금 하고 있는 목표
2. 최근 완료/진행 중 상태
3. 최근에 바뀐 결정
4. 반복되는 리스크나 블로커
5. 계속 봐야 하는 문서/파일/산출물 링크

### 5.3 카드 반영

1. `현재 상태`에는 지금 시점 설명만 남긴다.
2. `활성 컨텍스트`에는 최신 daily / plan / review만 남긴다.
3. `최근 결정`은 날짜 포함 1~3개만 유지한다.
4. `최근 블로커 / 리스크`는 지금 의미 있는 것만 남긴다.
5. 오래된 내용은 중복되면 지우고 최신 상태로 재정렬한다.

### 5.4 링크 정리

1. 프로젝트명은 저장소명이 아니라 프로젝트 카드 제목 기준으로 적는다.
2. 활성 plan은 가장 최신이면서 실제로 살아 있는 문서를 우선한다.
3. daily / review / plan 링크는 많아도 각 1개씩만 우선 노출한다.

## 6. 추출 규칙

- `오늘의 결정`, `Summary`, `Details (Agent Log)`에 있는 문장 중 프로젝트 전반에 영향을 주는 것만 올린다.
- 단순 실행 로그("테스트 실행", "파일 수정")는 그대로 올리지 않는다.
- 아래처럼 바뀐 상태를 요약하는 문장으로 재작성한다.

예:

- 원문: "`pnpm typecheck`, `pnpm build`, `pnpm build:stage` 통과"
- 카드 반영: "자동 검증은 대부분 통과했고, 남은 검증은 수동 E2E 증적 수집이다."

- 원문: "T17, T26은 사용자 진행"
- 카드 반영: "남은 수동 E2E 증적 수집은 사용자 진행 항목으로 분리했다."

## 7. 반영 우선순위

### 7.1 `현재 상태`

- 상태: active / paused / archived
- 현재 목표
- 현재 단계
- 우선순위

### 7.2 `활성 컨텍스트`

- 현재 활성 plan
- 최근 review
- 최근 daily

### 7.3 `최근 결정`

- 프로젝트 방향이나 작업 기준을 바꾸는 결정만 반영

### 7.4 `최근 블로커 / 리스크`

- 아직 살아 있는 리스크만 반영
- 이미 끝난 문제는 남기지 않는다

## 8. 실패 시 처리

- 관련 프로젝트 카드를 찾지 못하면 새로 만들지 말고 먼저 후보 프로젝트 문서를 찾는다.
- 소스 노트는 있는데 결정/리스크가 불분명하면 억지로 채우지 않는다.
- plan이 여러 개면 가장 최신 문서를 우선하되, 실제 active 여부가 애매하면 `활성 plan 후보`로 적는다.
- project 카드 갱신 근거가 약하면 daily 링크만 추가하고 내용 과장은 하지 않는다.

## 8.1 언제 바로 호출하는가

아래 상황이면 작업 직후 바로 호출하는 편이 좋다.

1. `issue-tracker`로 중요한 이슈를 해결했다.
2. `implement-from-plan`으로 phase 또는 핵심 milestone이 닫혔다.
3. `deep-planning` 또는 `obsidian-plan-reset` 이후 active plan이 바뀌었다.
4. 반복적으로 등장하던 리스크의 상태가 달라졌다.

## 9. 빠른 실행 예시

```text
입력:

- daily_note: [[daily/2026-03-17]]

- review_note: [[prompt/review/2026-03-12]]

결과:
- $OBSIDIAN_ROOT/projects/프로젝트명.md 의
  현재 상태 / 활성 컨텍스트 / 최근 결정 / 최근 블로커 갱신
```
