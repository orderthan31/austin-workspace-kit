## 1. 개요 및 규칙

- 이 스킬은 `obsidian-cli-guideline`의 경로 기준을 따른다.
- `PROJECT_ROOT`와 `OBSIDIAN_ROOT`를 섞지 않는다.
- 프로젝트명은 현재 코드 작업 디렉터리에서 얻되, 이슈 보드 탐색은 항상 `OBSIDIAN_ROOT` 기준으로 한다.
- 이 스킬은 사용자가 미리 작성해둔 옵시디언의 프로젝트별 이슈 보드를 기준으로 동작한다.
- 에이전트는 무단으로 새 이슈를 창조하지 않으며, 사용자가 "접수됨"에 등록한 항목을 가져와 처리하는 "실무자(Worker)" 역할을 수행한다.
- 이슈 보드는 `obsidian-kanban` 플러그인 형식(`kanban-plugin`)을 기본으로 가정한다.
- 카드 상태는 체크박스 문자보다 "어느 리스트에 들어 있는가"를 우선 기준으로 해석한다.
- 카드 한 줄에는 한 이슈만 적고, 날짜 메타는 줄 끝에 인라인으로 붙인다. 예: `➕ 2026-03-27`, `✅ 2026-03-27`
- 카드 첫 줄은 짧은 제목만 유지하고, 긴 배경 설명은 `[[BUG-xxx]]` 같은 별도 노트 링크로 분리한다.
- 이 스킬은 issue 보드만 갱신하고 끝나는 스킬이 아니다.
- 이슈를 읽었든, 옮겼든, 고쳤든, 막혔든 그 사실은 같은 날 `obsidian-daily-ops`에도 남기는 것을 기본으로 본다.
- 즉 `issue = 상태 보드`, `daily = 실제 작업 로그`로 역할을 분리한다.

## 2. 보드 탐색 및 작업 확인 (Pull)

- 현재 작업 중인 코드 프로젝트 디렉터리명에서 프로젝트명을 확인한다.
- 이 이름으로 vault 내부 경로 `$OBSIDIAN_ROOT/issue/<현재_프로젝트명>/` 를 본다.
- 즉 `issue/<현재_프로젝트명>/` 는 현재 프로젝트 상대경로가 아니라 옵시디언 볼트 상대경로다.
- 우선순위는 아래처럼 둔다.
  1. `$OBSIDIAN_ROOT/issue/<현재_프로젝트명>/Issue-Kanban.md`
  2. `$OBSIDIAN_ROOT/issue/<현재_프로젝트명>/` 아래의 다른 kanban 보드
- frontmatter에 `kanban-plugin` 키가 있고 하단 `%% kanban:settings` 블록이 있으면 플러그인 보드로 간주한다.
- `## 📥 접수됨 (To Do)` 리스트에 있는 미해결 카드(`- [ ]`) 목록을 우선 확인한다.
- `## ✅ 완료됨 (Done)` 리스트의 카드 줄 끝에 있는 `✅ YYYY-MM-DD`를 완료일로 읽는다.
- 사용자가 특정 버그를 지정하지 않았다면 목록 중 하나를 선택하고, 상세 버그 노트(`[[BUG-XXX]]`)가 연결되어 있다면 해당 파일도 함께 읽어 파악한다.

## 3. 계획 세분화 (deep-planning 연계)

- 선택한 이슈가 단순한 오타 수정이 아니라 요구사항이 거칠거나, 분석/설계가 필요한 규모라면 즉시 코딩에 돌입하지 않는다.
- 이 경우 `deep-planning` 스킬을 먼저 호출하여, 선택된 이슈를 구현 가능한 작업 명세로 정제하고 프로젝트 루트의 `plan.md`에 세분화(Breakdown)하여 기록한다.

## 4. 진행 상태로 변경 (In Progress)

- 작업(또는 계획 수립)을 시작할 때, 선택한 항목을 칸반 보드에서 `## 🏗️ 진행 중 (In Progress)` 섹션으로 이동시킨다.
- 플러그인 보드에서는 진행 상태를 별도 체크 문자로 표현하지 말고, 카드를 `진행 중` 레인으로 옮겨 상태를 표현한다.
- 미완료 카드의 체크박스는 기본적으로 `- [ ]` 를 유지한다.
- 진행 상태로 옮긴 뒤에는 같은 사실을 `obsidian-daily-ops`에도 남긴다.
  - 최소 기록: 어떤 이슈를 집었는지, 현재 상태, 다음 액션

## 5. 코드 구현 및 검증 (implement-from-plan 연계)

- `plan.md`가 생성되었거나 이미 존재하는 경우, 임의로 코드를 수정하지 말고 반드시 **`implement-from-plan` 스킬을 호출하여** 계획된 컨텍스트와 체크박스 순서에 따라 좁은 범위로 안전하게 구현한다.
- 매우 단순한 단일 파일 버그 픽스로서 `plan.md`를 거치지 않은 경우에 한해서만 직접 코드를 분석하고 수정한다.
- 수정을 마친 후, 프로젝트에 맞는 로컬 테스트(Lint, Typecheck, E2E 등)를 실행하여 검증한다.
- 자체 검증에 시간이 걸리거나 대기가 필요한 경우, 항목을 `## 🧪 검증 중 (Testing)` 섹션으로 임시 이동시킬 수 있다.
- 필요하면 카드 줄 끝에 관련 노트 링크나 생성일(`➕ YYYY-MM-DD`)을 유지하되, 한 카드에 과도한 설명을 길게 붙이지 않는다.
- 구현/검증 중간 결과도 의미 있는 변화면 `obsidian-daily-ops`에 남긴다.
  - 예: 원인 확인, 핵심 수정 완료, 테스트 실패, 재현 성공, 차단 발생

## 6. 작업 완료 처리 (Done)

- 모든 검증이 통과하고 이슈가 완전히 해결되면, 칸반 보드의 항목을 `## ✅ 완료됨 (Done)` 섹션으로 이동시킨다.
- 카드를 완료 레인으로 옮길 때는 상태를 `- [x]` 로 변경하고, 카드 줄 끝에 완료일 메타 `✅ YYYY-MM-DD` 를 붙인다.
- 생성일이 이미 있다면 `➕ YYYY-MM-DD` 메타는 유지하고, 완료일만 추가한다.
- 칸반 파일의 frontmatter `updated` 값도 같은 날짜로 갱신한다.
- `implement-from-plan`을 사용했다면 해당 스킬이 `plan.md`의 완료 상태를 갱신하도록 둔다.
- 가능하면 같은 완료 사실을 `obsidian-daily-ops`에도 같은 날짜 기준으로 남겨 daily 로그와 보드 날짜가 어긋나지 않게 한다.
- 상세 버그 파일(`BUG-XXX.md`)이 있다면, 해당 파일에 수정된 파일이나 해결 원인 등을 간략히 덧붙여 기록한다.
- 완료로 끝난 경우 아래를 같이 확인한다.
  1. daily에 완료 사실이 남았는가?
  2. 프로젝트의 최근 상태/결정/리스크가 바뀌었으면 `obsidian-context-ingest`로 project 카드 승격이 필요한가?

## 7. 공통 후처리

이 스킬은 아래 루프를 기본으로 따른다.

1. issue 보드 상태를 갱신한다.
2. 같은 사실을 `obsidian-daily-ops`에 남긴다.
3. 프로젝트 전반 상태가 바뀌었으면 `obsidian-context-ingest`까지 이어간다.

쉽게 말하면:

- issue만 바꾸고 끝내지 않는다.
- daily까지 남겨야 "오늘 무슨 작업을 했는지"가 보인다.
- project까지 승격해야 "지금 이 프로젝트 상태가 어떤지"가 보인다.
